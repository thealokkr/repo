# Acceptance evidence A1–A12

## Release 1 CLI evaluation scope

The development and validation gates evaluate system quality for the unattended, not-sent CLI. Ticket labels are read only after each run for evaluation. The CLI's final summary reports predicted intent classes, per-class support/prediction/correct counts, precision and recall, and comparisons for urgency, route, answerability, and protected cases. Run artifacts retain the confusion matrix and per-ticket comparisons. Exact agreement with every ticket label is not a completion condition.

The blocking system-quality KPI targets are intent precision of at least 85% per evaluable class; p95 processing latency under 3 seconds at the PRD v2.6 boundary; zero private-data occurrences in generated text; confidence calibration within 5 percentage points for each populated band; complete decision-log coverage; and zero automatic sends for protected cases. The scored latency includes retrieval through durable outcome/audit persistence and excludes only time waiting for the external draft-generation response. Report generation-request duration and full generation-inclusive latency separately. The Evaluation Framework says latency is measured end to end, including retrieval, but does not explicitly resolve generation timing; PRD v2.6 records the owner's interpretation for this release. Group-quality variation across comparable language-fluency and customer-plan groups retains an under-five-point target and is always reported, but PRD v2.6 makes it non-blocking for progression. For answer grounding, report citation resolution, eligible-source provenance, exact claim-to-passage traceability, expected-document coverage, and denominators for every generated draft. PRD v2.4 adds a required GPT-6 Luna judge sample of 20 generated drafts, with acceptance targets of response-quality proxy >=4/5, citation support >=95%, and <=5% of sampled responses containing an unsupported claim. These are LLM-judged acceptance measures, not human ratings or actual CSAT. CS-029 must implement them before the development gate can pass. The prior human evaluation of at least 50 responses by two assessors remains excluded. Urgency, route, and answerability are reported with confusion counts and trade-offs; no numeric accuracy cutoff is invented where the requirements specify none.

Availability, including the Evaluation Framework's 99.5% target, is excluded from the CLI KPI gate under the time-pressure scope. Business outcomes such as first-contact resolution, reply time, satisfaction, realized escalations, and repeat contacts are also outside this not-sent CLI evaluation. Predicted routes and answerability are model measures, not achieved customer outcomes.

## Operational reconciliation

For each batch, confirm `metrics.json` reports `evaluation.integrity.status` as `complete` and `evaluation.run_observed.technical.decision_log_reconciliation.value` as `1`; its evaluation section includes the expected input count, result count, decision count, missing indexes, and mismatched indexes. Reconcile that count with `results.jsonl`, `decision_log.jsonl`, SQLite `ticket_runs`, and SQLite `audit_events`, and inspect `exceptions.jsonl` for per-ticket failures. The runtime SQLite file is the durable decision record; JSONL and metrics files are per-run exports under a unique directory. A completed batch can contain `degrade` results and per-ticket exceptions while exiting `0`; startup, database, or export-finalization errors exit `1`. Calibration errors exit `2`.

The final development and validation gates both use the checked-in `data/policy/frozen_routing_policy.json`. Do not recalibrate between the two runs; validation is evaluated once against the development-frozen thresholds. The README's credential-free path remains suitable for smoke runs and checks output/database count reconciliation, but it cannot establish answer grounding where retrieval sources are unavailable.

Retrieval validates the checked-in index against packaged source hashes, the embedding model, and passage records before returning sources. The historical CS-020 run predates the CS-004 schema-3 freshness repair and also ran with query embeddings disabled. The raw metadata-manifest hash remains as original build provenance; schema-3 freshness is determined by the canonical passage-record digest and the current packaged Chroma records. The packaged-index integration test confirms local retrieval returns the current source ID without contacting an embedding service. The credential-backed source-ID completion gate has not been rerun and remains unverified. Rebuilding the index or making query-embedding requests calls the external OpenAI API and may incur charges. If the index or query embedding provider is unavailable, retrieval records an evidence gap and the ticket is safely escalated. The scored per-ticket processing latency includes normalization, classification, query embedding, retrieval, guardrails, and durable result/audit persistence; it excludes only the draft-generation response wait. Full generation-inclusive processing duration is reported separately. The p95 uses the nearest-rank method.

Create a recipient ZIP with `uv run python scripts/package_source.py --output dist/cloudserve-support.zip`. The command verifies archive integrity after writing. It includes project source, locked dependencies, the KB corpus and vector index, ticket/evaluation fixtures, policy, schemas, tests, and `.env.example`. It filters out `.env`/other local environment files, development-only `.agents/`, `.workarea/`, and `.codex/` folders, `.venv`, caches, bytecode, build directories, runtime SQLite state, and generated `outputs/` content; only the `.gitkeep` placeholders for runtime and output directories remain.

`OPENAI_API_KEY` must be supplied by the recipient through an ignored local `.env` or shell environment when an embedding or OpenAI inference request is wanted. No real credential is stored in source, `.env.example`, or the acceptance evidence. The supplied hidden evaluation set is unavailable here, so its one-shot run remains a recipient-side acceptance step.
